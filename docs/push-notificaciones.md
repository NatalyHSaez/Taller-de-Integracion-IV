# Preparación de notificaciones push — Grupo 9

## Instalación y configuración

Desde la raíz móvil, antes de incorporar el plugin en `app.json`, ejecutar `npx expo install expo-notifications expo-dev-client`. Expo elige versiones compatibles con el SDK 57 declarado; conservar los cambios de `package.json` y `package-lock.json`. `expo-constants` ya está instalado. No actualizar el SDK ni sustituir manualmente el lockfile.

El plugin `expo-notifications` configura el canal predeterminado `health-updates`. El adaptador crea el canal Android «Avisos de salud» cuando el usuario solicita permisos; importancia DEFAULT y visibilidad PRIVATE en bloqueo. No se habilita procesamiento remoto en segundo plano en iOS. No se piden alarmas exactas ni permisos adicionales ajenos a push. Los ajustes del usuario prevalecen. El contenido futuro deberá ser genérico, sin diagnóstico ni valores clínicos en el aviso.

## Probar permisos

- La pantalla Notificaciones tiene un panel para consultar el permiso y, si el sistema permite solicitarlo, hacerlo mediante un toque explícito. No se solicita al arrancar ni al iniciar sesión. El permiso es del dispositivo, no indica que la cuenta esté inscrita para push.
- Web y Expo Go se informan como no compatibles con este flujo de push; no se carga el módulo de notificaciones en esos entornos. Android e iOS requieren una compilación propia. La lectura de permiso no crea canales ni pide permisos; la solicitud crea el canal Android antes de solicitar al sistema. Si el sistema bloquea la solicitud, modificar en ajustes y volver a consultar.
- iOS distingue autorización plena, provisional, temporal, denegada y no determinada. No se interpreta la autorización provisional como plena.
- En Android, para una compilación local con JDK y Android Studio configurados, conectar un dispositivo y ejecutar `npx expo run:android`. Acordar previamente el identificador de aplicación con el equipo si Expo lo solicita. Para futuras sesiones del mismo cliente, `npx expo start --dev-client`. En iOS la compilación local requiere macOS/Xcode; desde Windows puede usarse EAS con las credenciales correspondientes. Expo Go y web siguen siendo opciones para validar funciones internas, no entrega push.
- Verificar `npx expo config --type prebuild` y `npx expo install --check` después de instalar. La configuración JS no modifica un binario ya instalado: compilar nuevamente cuando cambian los plugins nativos.

## Pendiente deliberado

No se inventa `projectId`, `android.package`, `ios.bundleIdentifier`, credenciales FCM/APNs ni una configuración EAS vinculada a una cuenta inexistente. Definirlos con el equipo antes de las pruebas de entrega. Grupos posteriores: obtención del token Expo, ciclo de vida y asociación con sesión, recepción/navegación, endpoints acordados con Integra II, desvinculación y entrega real. No registrar secretos ni tokens en Git o TXT. Los permisos no son un sistema de emergencias ni garantizan entrega.

Referencias oficiales: [Expo Notifications SDK 57](https://docs.expo.dev/versions/v57.0.0/sdk/notifications/), [configuración push](https://docs.expo.dev/push-notifications/push-notifications-setup/), [compilaciones locales](https://docs.expo.dev/guides/local-app-development/).

## Grupo 10: obtención del token Expo

Desde Notificaciones, consultar el permiso y pulsar «Comprobar token push» si está concedido (incluidos los estados provisional y temporal de iOS). No se solicita el permiso implícitamente ni se obtiene el token al arrancar. Se comprueba la sesión autenticada antes y después de la solicitud, y se vuelve a consultar el permiso antes de devolver un token válido. Las peticiones concurrentes de la misma sesión comparten la operación; una nueva comprobación vuelve a consultar Expo. En Android se prepara el canal antes de obtener el token.

El identificador del proyecto se obtiene de `Constants.expoConfig.extra.eas.projectId` o `Constants.easConfig.projectId`; si falta, no tiene formato UUID o ambos valores discrepan, no se llama al proveedor. Se requiere vincular el proyecto real del equipo con Expo/EAS, configurar identificadores de aplicación y credenciales de push según plataforma y compilar el cliente nativo. No se proporciona ningún UUID de ejemplo en la configuración. La obtención utiliza el servicio Expo, requiere conexión y puede fallar; el usuario puede reintentar. El token se mantiene únicamente durante la operación, no se imprime, muestra, copia ni guarda en almacenamiento local. La pantalla recibe solo el estado de la última comprobación, que no garantiza entrega ni vigencia posterior. La integración posterior debe gestionar rotación mediante el listener nativo y registrar/desvincular la instalación con el backend; no existe esa integración en este grupo. No enviar datos clínicos ni tokens a registros de diagnóstico.

## Grupo 11: puerto y casos de uso de dispositivos

`PushDevicePort` es un contrato **interno**, no un DTO ni una ruta HTTP aprobada. Recibe el token Expo, proyecto y plataforma, y un ámbito local de operación (`ownerId`, `AbortSignal`); el futuro adaptador deberá usar la sesión autenticada, no confiar en un identificador de usuario enviado por el cliente. Debe normalizar únicamente una confirmación verificable del servidor a `{ status: 'registered' | 'unregistered', deviceId }`. El identificador es opaco; el formato interno puede revisarse con el contrato definitivo. No se almacena el token ni se expone la confirmación con identificadores a la UI.

Los casos `registerPushDevice` y `unregisterPushDevice` no se conectan todavía a pantallas, login, logout ni tareas automáticas. Sin adaptador se devuelve `backend-not-configured` sin obtener token ni emitir HTTP. El registro exige sesión y permisos mediante el caso del Grupo 10, obtiene un token nuevo en cada operación y solo declara éxito con confirmación válida. Las operaciones iguales de una sesión comparten solicitud; otras operaciones concurrentes quedan bloqueadas (`busy`). Si cambia la sesión, se solicita cancelación al adaptador y se descarta la respuesta; cancelar una petición no garantiza revertir una escritura ya ejecutada por el servidor.

La desvinculación explícita solo utiliza una confirmación en memoria de la sesión activa, sin necesitar permiso push concedido. Si no existe esa confirmación, devuelve `not-confirmed`, no éxito. Una respuesta inválida, error o resultado incierto devuelve `unconfirmed`. Se permite reintentar, pero el servidor deberá garantizar idempotencia. Al cambiar de sesión se borra la confirmación local; **esto no desvincula el dispositivo en el servidor**. No hay persistencia de asociaciones, revocación al cerrar sesión ni rotación automática en este grupo. Para habilitar registro real es obligatorio acordar identidad estable de instalación, unicidad/rotación del token, idempotencia, desvinculación recuperable tras reinicio o fallo de red, revocación con logout y cambio de cuenta, y tratamiento de tokens inválidos. Las asociaciones no deben permitir que una instalación reciba avisos de una cuenta anterior. Hasta entonces no activar el envío remoto desde el backend.

Los datos ficticios del entorno local son registros de prueba del backend real (PostgreSQL, API Gateway y microservicios); no se usan mocks, tokens ficticios ni adaptadores de demostración en la aplicación productiva. Los dobles de prueba quedan exclusivamente en `tests/`.

## Grupo 12: recepción nativa mientras la app está en ejecución

La composición conecta `PushReceptionPort` con `expo-notifications.addNotificationReceivedListener`. La raíz monta un único ciclo de vida; la suscripción se crea solo con sesión backend autenticada y plataforma nativa compatible, se retira al cambiar de sesión o desmontar la raíz, y una suscripción que termina de instalarse tarde se elimina. La renovación de access token no reinicia el listener. Web y Expo Go no cargan el módulo. No se solicita permiso, obtiene token ni registra dispositivos desde este flujo.

Se descarta el evento completo (incluidos título, cuerpo, identificadores y datos personalizados). Solo se emite una señal sin payload para refrescar el listado interno del usuario actual si el almacén ya está vinculado a su sesión. Señales concurrentes se agrupan; si hay carga, paginación o marcado en curso, se conserva una actualización pendiente hasta que termine. Si el listado aún no se ha vinculado, su carga normal consultará al backend al abrirlo. No se insertan avisos locales, no se marcan como leídos automáticamente ni se modifican alertas clínicas. No hay navegación por pulsación, tareas headless ni procesamiento garantizado con la app cerrada. En SDK 57 no se instala un handler de presentación en primer plano; se conserva el comportamiento predeterminado de no mostrar banner nativo en primer plano.

La integración no implica entrega remota disponible: se requiere proyecto Expo/EAS, compilación nativa, registro real y envío por Integración II. El listener puede recibir eventos nativos, incluidos locales; no los distingue ni los considera prueba de entrega remota o autorización. No se prueba entrega real mediante mocks en producción. Las pruebas de contrato ejercitan exclusivamente dobles en `tests/`. No se habilita navegación hasta validar el contrato de payload y los permisos del servidor. Referencia: https://docs.expo.dev/versions/v57.0.0/sdk/notifications/.

## Grupo 13: navegación segura al pulsar un aviso

El adaptador nativo escucha `addNotificationResponseReceivedListener` y consulta `getLastNotificationResponse` al instalarse después de restaurar sesión y montar el navegador raíz. Solo la acción predeterminada de pulsación genera una señal. Se consume la última respuesta con `clearLastNotificationResponse` y se deduplican hasta 128 identificadores nativos en memoria por suscripción; no son identificadores clínicos ni se persisten. Las acciones personalizadas no navegan. No se interpreta `data`, título, texto, enlaces, rutas ni identificadores clínicos. Web y Expo Go no cargan el SDK. Se retira la suscripción al desmontar o dejar de estar listo el navegador; una instalación tardía se retira igualmente.

El caso de uso verifica la sesión backend actual y el estado de acceso de la aplicación: paciente autenticado o cuidador con paciente seleccionado previamente. La raíz permite únicamente `router.navigate('/notificaciones')`, sin parámetros. La pantalla existente consulta al servidor con la sesión actual; la pulsación no cambia de paciente, no concede permisos, no marca avisos ni crea registros. Si no hay sesión o selección necesaria, se descarta la señal, sin redirigir ni esperar un login futuro. La respuesta inicial solo se admite si había sesión al iniciar la suscripción y sigue siendo la misma. El identificador nativo no demuestra la cuenta destinataria ni cuándo se pulsó; incluso una respuesta conservada de una cuenta anterior solo puede abrir el listado propio de la cuenta actual. No se utiliza para abrir detalles. Si no hay respuesta inicial disponible o el router no puede navegar, se conserva la navegación manual. No se promete entrega ni apertura en frío en todos los estados del sistema; falta verificar con binario nativo.

Antes de activar envío remoto es necesario acordar el payload, validar destinatario y desvinculación efectiva con Integra II. La navegación específica por aviso o alerta queda fuera de este grupo. No se usa ningún endpoint nuevo, almacenamiento de avisos, dato simulado productivo ni handler de presentación. Referencia: https://docs.expo.dev/versions/v57.0.0/sdk/notifications/.
